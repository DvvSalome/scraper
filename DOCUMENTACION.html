Qué es

El problema que resuelve

Una operación de mensajería trabaja con varias transportadoras (Proships, X-Cargo, iMile, Pasarex). Cada una tiene su propio portal. El equipo necesita saber, por mensajero, qué paquetes siguen pendientes, generar reportes contables y avisar a cada repartidor. Scraper Timex centraliza eso: una página, cuatro herramientas, sin tocar Excel a mano.

Cómo encaja todo

Arquitectura de alto nivel

El navegador habla solo con server.py. El servidor escribe la lista de guías en un archivo, lanza el scraper correcto como proceso hijo y lee de vuelta su resultados.csv. El scraper, por su cuenta, abre Chrome y navega los portales reales.

HTTP / JSON lanza proceso navega web real produce archivos
⚠️
Estado en memoria. Los diccionarios SCRAPER_STATES y PASAREX_ASSIGN_STATE viven dentro del proceso del servidor. Si reinicias server.py, se pierde el estado de ejecución (no los CSV, que quedan en disco). No hay cola ni persistencia real.

Anatomía

Cómo funcionan las integraciones

Cada proveedor es un script Python autocontenido que cumple un contrato simple: leer una lista de guías, scrapear, y escribir un CSV. El servidor solo sabe arrancar el proceso y leer su salida. Nada más.

Guía práctica

Cómo agregar un nuevo proveedor

Son 4 pasos: script, registro en el servidor, tarjeta en la UI, y verificar el contrato de salida. Tiempo estimado: 1–2 días dependiendo de complejidad del portal.

1

Crear la carpeta y el script del spider

Copia la estructura de iMile como plantilla — es la más limpia. Renombra y adapta.

# Estructura mínima del script
import os, csv, time
from pathlib import Path
from selenium import webdriver
from selenium.webdriver.common.by import By
from selenium.webdriver.support.ui import WebDriverWait
from selenium.webdriver.support import expected_conditions as EC
import chromedriver_autoinstaller

# Credenciales desde env (nunca hardcodeadas)
EMAIL    = os.getenv("NUEVO_EMAIL", "")
PASSWORD = os.getenv("NUEVO_PASSWORD", "")
BASE_URL = "https://portal.nuevo-proveedor.com"

def build_driver():
    chromedriver_autoinstaller.install()
    opts = webdriver.ChromeOptions()
    opts.add_argument("--no-sandbox")
    opts.add_argument("--disable-dev-shm-usage")
    opts.add_argument("--disable-blink-features=AutomationControlled")
    # headless solo si NO necesitas QR/captcha
    return webdriver.Chrome(options=opts)

def login(driver):
    driver.get(f"{BASE_URL}/login")
    WebDriverWait(driver, 30).until(
        EC.presence_of_element_located((By.CSS_SELECTOR, "input[name='email']"))
    )
    driver.find_element(By.CSS_SELECTOR, "input[name='email']").send_keys(EMAIL)
    driver.find_element(By.CSS_SELECTOR, "input[name='password']").send_keys(PASSWORD)
    driver.find_element(By.CSS_SELECTOR, "button[type='submit']").click()
    WebDriverWait(driver, 30).until(lambda d: "/login" not in d.current_url)
    print("✅ Login OK")

def scrape_guia(driver, guia):
    # Adaptar a la UI del proveedor
    driver.get(f"{BASE_URL}/tracking?q={guia}")
    # ... extraer campos ...
    return {
        "tracking": guia,
        "status": "",        # checkpoint del proveedor
        "fecha": "",         # del PackTrack
        "cliente_direccion": "",
        "cliente_nombre": "",
        "cliente_numero": "",
        "municipio": "",
        "mensajero": "",     # del PackTrack
        "estado": "",        # del PackTrack
    }

def main():
    codes = [l.strip() for l in Path("paquetes.txt").read_text(encoding="utf-8").splitlines() if l.strip()]
    if not codes:
        print("⚠️ paquetes.txt vacío")
        return

    driver = build_driver()
    results = []
    try:
        login(driver)
        for i, code in enumerate(codes, 1):
            print(f"=========== [{i}/{len(codes)}] {code} ===========")
            data = scrape_guia(driver, code)
            results.append(data)
            time.sleep(1.0)
    finally:
        driver.quit()

    # OBLIGATORIO: escribir resultados.csv con exactamente estas 10 columnas
    with open("resultados.csv", "w", newline="", encoding="utf-8") as f:
        w = csv.writer(f)
        w.writerow(["tracking","status","fecha","tracking",
                    "cliente_direccion","cliente_nombre","cliente_numero",
                    "municipio","mensajero","estado"])
        for r in results:
            w.writerow([r["tracking"], r["status"], r["fecha"], r["tracking"],
                        r["cliente_direccion"], r["cliente_nombre"], r["cliente_numero"],
                        r["municipio"], r["mensajero"], r["estado"]])
    print("📁 Listo: resultados.csv generado.")

if __name__ == "__main__":
    main()

✅ Checklist antes de dar por terminada la integración

  • Sin credenciales en código: solo os.getenv() sin valor por defecto hardcodeado.
  • CSV con 10 columnas en el orden correcto (verifica con head -1 resultados.csv | tr , '\n' | nl).
  • Script termina con exit 0 si todo fue bien, exit ≠ 0 si hubo error — el servidor lo usa para detectar éxito/fallo.
  • Sin input() bloqueante en el flujo principal — el servidor no tiene stdin para el proceso hijo.
  • Lee paquetes.txt desde Path("paquetes.txt") (relativo al CWD que setea el servidor).
  • Escribe resultados.csv en el mismo directorio.
  • Probado con RUN_SPIDERS=0: la UI muestra la tarjeta, el status cambia, los botones de descarga responden.
  • Probado con RUN_SPIDERS=1 con al menos 3 guías reales.
El patrón central

El cruce con PackTrack

Esta es la idea que se repite en casi todos los spiders y conviene entenderla una sola vez. Ningún portal de transportadora sabe qué mensajero local lleva el paquete ni su celular. Eso vive en PackTrack (una app Rails en packtrack.site). Por eso cada spider abre dos sesiones a la vez.

①

Portal transportadora

Login en el sitio del proveedor. Por cada guía: estado/checkpoint, nombre del cliente, dirección, teléfono.

②

PackTrack /paquetes

GET /paquetes?codigo=GUIA. Localiza la fila por número de guía y saca fecha, mensajero y estado local.

③

PackTrack /mensajeros

GET /mensajeros?query=NOMBRE. Con el nombre del mensajero busca su celular para el aviso de WhatsApp.

🔗
El resultado final de cada guía es la fusión de las tres consultas. Las columnas marcadas cliente_* vienen del portal de la transportadora; fecha, mensajero y estado suelen ganar los de PackTrack. La selección de columnas es tolerante: busca por nombre de cabecera (mensajero, courier, driver…) y si no, cae a una posición fija.

3

El servidor prepara y lanza

Escribe paquetes.txt en la carpeta del proveedor, fija SEND_WHATSAPP=1 si aplica y lanza el spider con subprocess.Popen([sys.executable, script]). Un hilo watcher espera el final. Solo aquí se respeta RUN_SPIDERS: si es 0, devuelve datos simulados.

4

El spider trabaja (doble sesión)

Abre Chrome, loguea en el portal del proveedor y en PackTrack en pestañas separadas. Por cada guía hace el cruce de 3 consultas y arma una fila. Pausa ~1s entre guías.

Cómo Proships le dice al mensajero cuántos días lleva pendiente cada paquete

El spider de Proships no manda una lista plana: arma un solo mensaje por mensajero y agrupa los paquetes por antigüedad en días, de más viejo a más reciente, para que el repartidor vea de un vistazo qué lleva más tiempo sin entregar. Toda la lógica vive en proships_spider_with_whatsapp_v2.py.

Qué hace, paso a paso

  • Agrupa por mensajero. Junta todas las guías por (mensajero, celular); descarta filas sin mensajero o sin celular.
  • Filtra pendientes. is_pendiente() deja fuera lo que contenga entregado / delivered / devolución / devuelto / return / retorno en estado o checkpoint.
  • Calcula los días. days_ago() parsea la fecha en formato dd/mm/YYYY y resta contra hoy → número de días pendiente.
  • Hace buckets por día y los recorre de mayor a menor (los más atrasados primero), con encabezado Pendientes de hace X día(s):.
  • Cada paquete sale como una línea Fecha, Guía, Cliente, Dirección. Lo envía por WhatsApp Web y lo vuelca a mensajes_whatsapp.csv.

El cálculo de días

def days_ago(fecha_str):
    d = datetime.strptime(
        fecha_str.strip(), "%d/%m/%Y").date()
    # hoy menos la fecha de la guía
    return (datetime.now().date() - d).days

buckets = defaultdict(list)
for it in items:
    if not is_pendiente(it["estado"],
                        it["checkpoint_code"]):
        continue                 # salta entregados/devueltos
    da = days_ago(it["fecha"])
    buckets[da].append(it)       # agrupa por antigüedad

# más viejo primero
for da in sorted(buckets, reverse=True):
    lineas.append(f"\nPendientes de hace {da} día(s):")

Honestidad técnica

Verdad sin maquillaje

Lo que la documentación bonita suele esconder. Todo esto está confirmado leyendo el código, no asumido.

🔓 Credenciales reales embebidas en el código ›
Casi todos los scripts traen email + contraseña reales como valores por defecto de os.getenv (Proships, BigSmart, PackTrack, Pasarex, iMile). El asignador de Pasarex incluye 24 credenciales completas (usuario + clave + placa). Cualquiera con acceso al repo las tiene. Deberían moverse a variables de entorno o un gestor de secretos.
🪟 Ruta de perfil Windows en el spider de Pasarex ›
El spider y el asignador de Pasarex apuntan a C:\Users\jhami\AppData\Local\Google\Chrome\User Data con Profile 3. En este host Linux esa ruta no existe — fallaría tal cual. Probablemente se desarrolló en la máquina de un operador concreto.
🧟 Código muerto y endpoints rotos ›
  • POST /api/process referencia contabilidad_data, que no existe en su ámbito → NameError. Ningún frontend lo usa.
  • El bloque de contabilidad de app.js llama a /api/contabilidad/empresas y /results, que no existen en el servidor. Es código inerte: la página real de contabilidad usa contabilidad/contabilidad.js.
  • Varios spiders tienen bloques tras un return/finally que nunca se ejecutan (lógica duplicada de WhatsApp, normalizadores sin usar).
  • asignar_proships.py sube el archivo dos veces y termina con un input() bloqueante.
🚫 Funciones desactivadas o falsas ›
  • Pasarex está deshabilitado en las 3 pantallas que lo mencionan (pendientes, asignación, contabilidad), aunque el backend conserva la lógica.
  • Asignación iMile es un placebo: el servidor responde OK al instante y el script solo imprime STATUS: OK. No asigna nada real.
  • El "Descargar Excel" de pendientes no es un xlsx real, es HTML con extensión .xls.
🧱 Fragilidad y rendimiento ›
  • Selectores CSS/XPath muy específicos y muchos time.sleep fijos: lento y quebradizo ante cambios de UI.
  • Columna municipio casi siempre vacía; cabecera tracking duplicada en el CSV.
  • El generador de Novedades reabre y guarda el Excel completo en cada fila (O(n) por guía).
  • Llamadas a subproceso inconsistentes: pendientes usa sys.executable, los demás usan "python3" (puede saltarse el venv — está documentado como error conocido en el README).
🐳 Docker arranca en simulado e incompleto ›
El Dockerfile instala selenium webdriver-manager openpyxl requests scrapy — le faltan chromedriver-autoinstaller, scrapy-playwright y pandas que sí usa el código. No define RUN_SPIDERS (queda en 0 → simulado) ni incluye un display para Chrome visible. Sirve para la UI, no para scraping real tal cual.
✅
En resumen: la arquitectura UI → servidor → subproceso → CSV es sólida y fácil de seguir. Las grietas están en seguridad (secretos en código), portabilidad (rutas/headless) y en funciones que se muestran en la UI pero no operan (Pasarex, asignación iMile). Saberlo evita sorpresas.
